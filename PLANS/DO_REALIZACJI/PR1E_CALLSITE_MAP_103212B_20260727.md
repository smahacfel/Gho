# PR1E — autorytatywna mapa callsite’ów cutoveru

Data zamrożenia: 2026-07-27
Base: `103212b16bfc059db367e1ceb3c7d00fd307d6c5`
Gałąź: `agent/ingest-state-quote-boundary-pr1e-20260727`

## 1. Zakres mapy

Mapa obejmuje wyłącznie aktywną ścieżkę:

```text
Yellowstone/Seer
→ IPC
→ PumpObservationLedgerV1
→ Event Bus
→ OracleRuntime
→ per-pool session / approved-or-committed state owner
→ canonical apply acknowledgement
→ CandidateIntegrity
→ MFS
→ Gatekeeper
→ Trigger execution handoff
```

Nie obejmuje testowych konstruktorów `GhostEvent`, historycznych helperów
scoringowych, offline replay ani NLN artifact writerów.

## 2. Emitery aktywnych zdarzeń strukturalnych

Repozytoryjne wyszukanie aktywnego kodu produkcyjnego wykazało dokładnie po
jednym emiterze:

| Zdarzenie | Jedyny aktywny emiter | Funkcja |
|---|---|---|
| `NewPoolDetected` | `ghost-launcher/src/components/seer.rs` | `process_pool_detected_event_for_session_gate()` |
| `PoolTransaction` | `ghost-launcher/src/components/seer.rs` | `emit_pool_transaction_to_event_bus()` |

Pozostałe wywołania konstruktorów tych `GhostEvent` znajdują się w testach,
fixtures/examples albo w kodzie odbiorców i nie są drugim produkcyjnym
emiterem.

W PR1E oba emitery muszą wymagać prywatnego
`CanonicalRuntimePermitV1`. Sam wrapper `PrimaryAuthority` nie daje prawa
emisji.

## 3. Granica Seer IPC i Ledgera

Aktywne callsite’y:

- `ghost-launcher/src/components/seer.rs`
  - `SeerEvent::PoolDetected` w `run()`;
  - `SeerEvent::Trade` w `run()`;
  - `ingest_pump_observation()`;
  - `pool_candidate_matches_primary_observation()`;
  - `trade_matches_primary_observation()`;
  - `finalize_pump_observation_ledger()`.

Stan bazowy:

- `ingest_pump_observation()` zwraca
  `Option<CanonicalMutationApplyReceiptV1>`;
- brak observation, poison Ledgera, failure stagingu albo sealowania pozwala
  parentowemu wrapperowi kontynuować;
- primary wrapper może dojść do emitera mimo braku canonical mutation;
- secondary raw i NLN są już witness-only;
- wrapper/observation mismatch jest dowodem shadow, lecz nie blokuje parentowej
  emisji.

Stan docelowy:

- `ingest_pump_observation()` zwraca typed
  `CanonicalRuntimeAdmissionV1`;
- tylko `Apply(CanonicalRuntimePermitV1)` może dojść do emitera;
- `NoApply` nie emituje;
- `Blocked` zamyka admission nowych kandydatów, ale nie zatrzymuje ochrony
  potwierdzonych pozycji;
- nie istnieje per-event fallback do parentowej emisji.

## 4. Bufory i replay wymagające zachowania permitu

### 4.1. Seer session/pool trade bridge

Plik: `ghost-launcher/src/components/seer.rs`

Typy i funkcje:

- `SessionPoolTradeBridge`;
- `BufferedCanonicalTradeV1`;
- `SessionTradeFlushResult::replay_ready`;
- `SessionPoolTradeBridge::ingest_trade()`;
- `SessionPoolTradeBridge::register_detected_pool()`;
- `SessionPoolTradeBridge::prune_expired()`;
- `SessionPoolTradeBridge::evict_oldest_pending_trade()`;
- `process_trade_event_for_session_gate()`;
- `process_pool_detected_event_for_session_gate()`.

Stan bazowy zawiera bounded pending-trade storage, lecz aktywny
`ingest_trade()` dla nieznanej puli zwraca `SilentDrop`; replay type przechowuje
sam `TradeEvent`. PR1E musi użyć `BufferedCanonicalTradeV1`, przenosić dokładnie
pierwotny permit i failować receipt przy expiry/eviction.

### 4.2. Oracle tx-first/orphan lane

Plik: `ghost-launcher/src/oracle_runtime.rs`

Typy i funkcje:

- `OracleRuntime::register_pool_tx()`;
- `OracleRuntime::drain_registration_orphans()`;
- `OrphanTx`;
- branch `GhostEvent::PoolTransaction` dla nieznanej puli.

Stan bazowy buforuje compatibility metadata bez canonical apply receiptu.
Aktywny canonical event z permitem nie może wejść do tej ścieżki jako sam
`PoolTransaction`. Albo permit jest zachowany do rzeczywistego apply, albo
receipt jest deterministycznie failowany.

### 4.3. Per-pool mpsc

Plik: `ghost-launcher/src/oracle_runtime.rs`

- `PoolObservationMsg::Transaction`;
- `PoolObservationMsg::NewPool`;
- `PoolTaskHandle`;
- `enqueue_pool_observation_msg()`;
- `pool_observation_task()`.

Ta kolejka już przenosi apply receipt. `Delivered` oznacza tylko enqueue, nie
apply. Lag/drop/closed/full musi failować receipt i nie może wytworzyć
`Ready`.

### 4.4. Approved/committed relay

Plik: `ghost-launcher/src/oracle_runtime.rs`

- `OracleRuntime::forward_approved_tx_to_commit_or_live_pipeline()`;
- `LauncherCommitCoordinator::add_approved_tx()`;
- `LivePipeline::process_event()`.

`BufferedHistory` oraz `PendingLive` nie są dowodem apply.
Tylko prywatny `CanonicalMutationApplyOutcomeV1::AppliedNewMutation`
potwierdza receipt.

### 4.5. BUY-path event consumption

Plik: `ghost-launcher/src/oracle_runtime.rs`

- `hydrate_buy_path_metadata()`;
- `wait_for_live_trigger_readiness()`;
- `wait_for_active_buy_route_evidence()`;
- `apply_active_buy_route_evidence_message()`;
- `execute_gatekeeper_buy_path()`.

Te funkcje mogą odebrać `PoolObservationMsg` podczas przygotowania BUY. Każdy
receipt musi zostać albo zastosowany przez rzeczywistego state ownera, albo
failowany; samo użycie zdarzenia jako evidence nie jest apply.

### 4.6. Witness-only bufory

Bufory `NlnTradePoolIdentityResolver` oraz NLN writer pozostają witness-only.
Ich replay nie może wytwarzać `PoolTransaction`, permitu ani canonical apply.

## 5. Rzeczywisty downstream state owner

### Trade

Plik: `ghost-launcher/src/session/observation.rs`

- `PoolObservationSession::ingest_transaction_with_apply_result()`;
- prywatny `CanonicalMutationApplyOutcomeV1`.

W per-pool tasku wynik jest przekazywany do
`resolve_canonical_apply()`. Tylko `AppliedNewMutation` może wywołać
`mark_canonical_apply_succeeded()`. `Duplicate`, `Ignored`, `Terminal` i
`Failed` failują receipt.

Approved/committed relay ma analogiczny state-owner result z
`forward_approved_tx_to_commit_or_live_pipeline()`.

### InitializePool

Plik: `ghost-launcher/src/oracle_runtime.rs`

- `register_new_pool_with_apply_outcome()`;
- `register_runtime_pool_detection()`;
- `pool_observation_task()`.

`AppliedNewMutation` wymaga nowej, jednoznacznej instalacji identity/runtime
state. Istniejąca ta sama rejestracja jest `Duplicate`, alias conflict jest
`Failed`. Samo utworzenie taska albo enqueue nie potwierdza apply.

## 6. CandidateIntegrity i apply fence

Plik: `ghost-launcher/src/candidate_integrity.rs`

Jeden współdzielony `CandidateIntegrityRegistry` zawiera:

- jeden prywatny, bounded `CanonicalApplyFenceV1`;
- `stage_canonical_mutation()`;
- `seal_complete_transaction_inventory()`;
- exact receipt lookup dla initialize/trade;
- `mark_canonical_apply_succeeded()`;
- `fail_canonical_apply()`;
- generation/CAS;
- `evaluation_guard()`;
- `submit_guard()`;
- pełną macierz lifecycle.

Jedyny aktywny producent `CandidateIntegrityOutcomeV1::Ready` pozostaje
prywatną ścieżką `publish_ready_with_cas()` po downstream apply.

Współdzielenie instancji:

- `ghost-launcher/src/main.rs` pobiera registry z `OracleRuntime`;
- dokładnie tę samą `Arc<CandidateIntegrityRegistry>` przekazuje do Seera.

PR1E nie tworzy drugiego registry ani drugiego fence.

## 7. MFS, evaluation i Gatekeeper

Plik: `ghost-launcher/src/oracle_runtime.rs`

Aktywna granica:

- `try_evaluate_feature_driven_terminal_verdict()`;
- `try_materialize_terminal_features()`;
- `PoolObservationSession::try_materialize_features()`;
- `GatekeeperBuffer::evaluate_from_features()`.

Stan bazowy:

- `open_candidate_integrity_evaluation_guard()` jest observe-only;
- brak guarda nie blokuje materializacji;
- `mark_mfs_materialized()` i `mark_evaluation_running()` są telemetryczne;
- terminal publish failure nie zatrzymuje strategicznego verdictu.

Stan docelowy:

```text
evaluation_guard
→ check_ready
→ build immutable MFS
→ check_ready
→ mark_mfs_materialized
→ check_ready
→ mark_evaluation_running
→ policy evaluation
→ check_ready
→ terminal publish / submit guard
```

Invalidation powoduje wyłącznie prywatny technical abort. Nie tworzy
`REJECT`, `TIMEOUT` ani policy reason.

## 8. Submit i lifecycle pozycji

Plik: `ghost-launcher/src/oracle_runtime.rs`

Callsite wykonawczy:

- `execute_gatekeeper_buy_path()`;
- `execute_gatekeeper_buy_via_trigger_with_fsc_gate()`;
- `TriggerComponent::execute_buy()` albo
  `dispatch_prepared_buy_with_shadow()`;
- `apply_trigger_dispatch_receipt_with_builder_mode()`;
- `apply_trigger_buy_outcome()`.

PR1E musi przenieść jeden istniejący
`CandidateIntegritySubmitGuardV1` od terminalnego BUY do bezpośredniej granicy
przed dispatch:

- invalid przed `try_begin_submit()` — zero sender calls, cancellation i
  jednokrotne zwolnienie capacity;
- po `try_begin_submit()` — brak fałszywego cancellation, ustawienie
  reconciliation required;
- po confirmation — późny witness conflict jest quarantine/audit i nie
  przerywa Position Managera, monitoringu ani protective exits.

Tryb wykonawczy, routing, quote math, sizing oraz TP/SL pozostają bez zmian.

## 9. AccountStateCore

Pliki:

- `ghost-core/src/account_state_core/reducer.rs`;
- aktywny odbiorca `GhostEvent::AccountUpdate` w
  `ghost-launcher/src/oracle_runtime.rs`.

Jedyną granicą AccountUpdate pozostaje PR1C
`AccountObservationArbiter`. Tylko
`AccountObservationOutcomeV1::AppliedNewMutation` mutuje stan.
CandidateIntegrity nie filtruje raw-primary AccountUpdate dla potwierdzonej
pozycji.

## 10. Startup i continuity

Pliki:

- `ghost-launcher/src/main.rs`;
- `ghost-launcher/src/components/seer.rs`;
- `off-chain/components/seer/src/grpc_connection.rs`;
- `off-chain/components/seer/src/ipc.rs`;
- `off-chain/components/seer/src/lib.rs`.

Istniejące kontrakty:

- dokładnie jeden skonfigurowany primary provider;
- stabilne i unikalne provider IDs;
- niezerowa ingress queue;
- Oracle startuje przed Seerem;
- jedna registry instance jest dzielona przez Oracle i Seer.

PR1E dodaje preflight:

- dostępny ledger i registry;
- niezerowe bounded capacities;
- aktywny downstream acknowledgement;
- aktywny AccountObservationArbiter;
- brak direct NLN/secondary canonical emission;
- `Pr1AuthorityEpochV1`.

`PoolDetectionRuntimeDispositionV1` docelowo:

- `CandidateAdmission` z aliasem serde `observe`;
- `ContinuityOnly`;
- `Suppressed`.

`ContinuityOnly` nie tworzy nowej sesji, MFS, Gatekeepera ani BUY.

## 11. Brak drugiego produkcyjnego authority

Po cutoverze dozwolone są wyłącznie:

```text
primary wrapper + aligned observation
→ PumpObservationLedgerV1 canonical mutation
→ CanonicalRuntimePermitV1
→ jedyny Event Bus emiter
→ exact receipt lookup
→ rzeczywisty downstream apply
→ Ready/CAS
```

Zabronione i objęte testem bypass guard:

- wrapper bez permitu;
- missing observation fallback;
- ledger/registry unavailable fallback;
- replay trade bez permitu;
- secondary/NLN Event Bus emission;
- receipt ambiguity;
- Event Bus enqueue traktowany jako apply;
- bezpośrednie MFS/Gatekeeper bez `Ready`;
- sender bez submit guard.

## 12. Stan po implementacji 1E-B

Mapa została zweryfikowana ponownie na finalnym diffie:

- jedynymi produkcyjnymi emiterami strukturalnymi pozostają funkcje z sekcji
  2 i oba wymagają `CanonicalRuntimePermitV1`;
- `SessionPoolTradeBridge` przechowuje trade razem z oryginalnym permitem;
- tx-first bez znanej puli nie wchodzi do legacy orphan lane, lecz failuje
  exact receipt;
- per-pool mpsc przenosi permit, ale enqueue nie potwierdza apply;
- wyłącznie `AppliedNewMutation` potwierdza receipt;
- MFS/evaluation i sender używają guarda z tej samej instancji registry;
- `ContinuityOnly` ma zero nowych strukturalnych emisji;
- AccountUpdate i protective handling istniejącej pozycji nie zależą od
  CandidateIntegrity nowych kandydatów;
- nie znaleziono drugiego produkcyjnego emitera, drugiego Ledgera, drugiego
  apply fence ani legacy fallbacku.
